## 一、skills-manager 架构速读（源事实，均可在仓库验证）

分四层，**最值得借鉴的是"接口薄、核心厚"**：

1. **存储层**：技能文件夹（`~/.skills-manager/skills/<skill>/`）是唯一真相源；SQLite 只是可重建的索引（DB 不进 git，文件进 git，快照=git tag）。好处：数据永远可手工修复、可迁移。
2. **领域核心**（Rust，无 UI 依赖，`src-tauri/src/core/`）：安装器（git/本地/skills.sh 三类来源）、目录扫描与收编（scanner/project_scanner）、同步引擎（symlink 或 copy 到各工具技能目录）、工具适配器（16 个 AI 工具的路径与检测）、预设服务（技能分组启停）、git 备份、跨进程锁 + SQLite WAL（GUI/CLI/MCP 三进程并发安全）。
3. **接口层 ×3**：同一核心，三个入口——桌面 GUI、CLI、MCP 服务器（21 个工具）。MCP 层已验证"AI 对话即管理界面"可行。
4. **Package 的处理方式**：不落库，前端展示时纯函数派生（同源且 ≥2 个技能才成包）。

### 需求 4 的数据源现实盘点（源事实与推断分开标）

- **调用行为数据**（事实）：Claude Code 会话记录（JSONL transcript）中含 Skill 工具调用记录，可离线挖掘"哪个 skill 被调过、频次"。
- **市场热度**（事实）：skills.sh 有安装量/榜单数据。
- **重复度**（推断，可行性高）：对 skill description/SKILL.md 做相似度聚类或 LLM 判重。
- **"调用质量"**（缺口）：没有任何现成数据。需要你自己定义评测口径——什么叫"这次调用是好的"？谁标注？多少样本？这正是 AI PM 的 P2 核心课，也是面试必问项。
- **"用户采用率"**（需澄清口径）：单机单用户场景下"采用率"=什么？建议改为"近 N 天调用频次/最近一次调用时间"，冷启动（新装 skill 无数据）怎么办要写进 PRD。

## 三、必须由你拍板的 5 个决策（D1-D5）

> D1 就是你面试没答上的第二题。这次是真实决策，答案会写进你自己的产品。

**D1 · Package 是实体还是派生？**
- A. 导入时落库，一等实体（有 package 表，skill 有外键）——查询/批量操作天然支持，但改名/移动/部分删除时要维护一致性
- B. 展示时派生（skills-manager 现状）——零迁移成本、永不脏数据，但每个界面都要重算，AI 侧不能直接"按包操作"
- C. 混合：落库缓存 + 可随时从来源字段重建
- 考虑因素：你的核心场景是"AI 按包管理"，MCP 工具需不需要稳定的 package id？

**D2 · 产品形态与技术栈？**
- A. 桌面 GUI 优先（Tauri/Electron）——直观，但等于重造 skills-manager 已解决的问题，周期长
- B. **MCP-first**：核心库 + MCP 服务器，AI 对话就是主界面，GUI 后置——差异化集中、2-3 周可出成果，但无图形界面演示性弱
- C. 本地 Web 服务（浏览器 UI + API）——折中，多一层服务管理
- 考虑因素：你的需求 4 说"通过 Code 上的问答来管理"——主界面到底是谁？

**D3 · MVP 砍到哪？**
- 五项需求全做 = 数月。V1 建议只留"不可妥协的最小闭环"，其余进 V2/V3。你来划：V1 必须有哪三个功能？排行榜和弹窗 UI 进不进 V1？

**D4 · 冗余筛选的指标口径？**
- 调用质量与采用率各自的定义、数据来源、冷启动策略、误杀（把有用 skill 判冗余）的兜底——至少给出 V1 能落地的一版口径，允许粗糙但必须可执行。

**D5 · 与现有 63 个 skill 的关系？**
- A. 兼容 skills-manager 的目录格式，直接读同一个中央库（无迁移，但被旧格式绑住）
- B. 新格式 + 一次性迁移工具（自由，但迁移是真实工程量）
- C. 只管新装的，旧的不动（最快，但"减少冗余"目标覆盖不到存量）

### D4 返工作业（W1 任务 1 返工项）

重写冗余口径，必须回答三问：
1. 指标如何区分"一个技能被高频爱用"与"多个技能在抢同一个活"？高频 ≠ 冗余，冗余 = 职责重叠。
2. 纯被动数据里，"被采用/有效"观测哪个信号？定义到日志字段级（调用了就算？调用后任务完成算？连续追问算失败？）。
3. 窗口为什么是 3 天？月用一次但不可替代的技能如何不被误杀？没有任何调用记录的新技能（冷启动）怎么处理？

交付格式：指标名 + 计算规则 + 数据来源 + 窗口 + 冷启动策略 + 误杀兜底，写成一段可执行的文字。

### D4 定稿：冗余口径「两段式·组内裁决」（2026-08-10 学习者选定：两段式 + 隔离区）

**第一段 · 分组（嫌疑检测，只回答"谁在抢同一个活"）**
- 输入：全部技能的 SKILL.md（name + description + 触发条件段落）
- 规则：语义相似度聚类（embedding 相似度初筛 + LLM 复核边界对），职责重叠 ≥ 阈值（初始 0.8，可调参）的技能进同一"职责组"；≥2 个技能才成组，并由 LLM 给每组生成一句"这组抢的是什么活"
- **组外技能永不参与冗余判定**——独门低频技能（如年度报税类）天然豁免，从机制上消灭低频误杀
- 触发时机：导入/更新技能时增量重算，每周全量重算一次
- 冷启动友好：分组只用描述文本，第一天就能对全部 63 个技能出组

**第二段 · 裁决（只在组内比较，只用被动数据）**
- 数据来源：Claude Code / Codex 会话日志（JSONL transcript）中的技能调用事件（技能名、时间戳、会话 ID）
- 窗口：滚动 **90 天**（放弃原 3 天方案：低频技能需要长窗口积累证据）
- 组内指标：① 调用份额 = 本技能 90 天调用次数 ÷ 组内总调用次数；② 距最近一次调用天数；③ 替换信号（数据充足时启用）：同一会话内先调 A 再调同组 B，A 记一次"被替换"
- 裁决规则（V1 简版）：组内份额 < 15% 且 90 天调用 ≤ 1 次 → 标记"建议隔离"；组内份额最高者永不标记
- 冷启动保护：技能导入不足 30 天、或组内总调用 < 10 次 → 该组仅显示"观察中"，不出裁决

**处置 · 隔离区（误杀兜底）**
- "建议隔离"必须用户在报告里一键确认后生效：从所有 agent 目录撤下同步，中央库保留文件与数据
- 隔离期 30 天内一键恢复（含原同步状态）；到期后提示归档/删除，仍需手工确认，**永不自动删除**
- 每次隔离/恢复写操作日志，出问题可追溯"这个任务干不动是因为哪个技能被隔离了"

**欠账登记（2026-08-10 全部结清）**：D1 理由随翻案交清（真实使用验证 + V1 无包实体需求）；D4 理由已交（组外豁免保护低频核心技能）。PRD v1 就此通过评审。
